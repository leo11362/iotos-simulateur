C'est quoi IoToS

IoToS (« Internet of Things Operating System ») est un micro-système d'exploitation pour Arduino UNO R4 Minima avec un Ethernet Shield 2. Il transforme la carte en petite « prise IP » pilotable de trois façons : par une ligne de commande, par une page web et par FTP.

Concrètement, tu branches la carte au réseau et tu obtiens, sans rien programmer :

  • une ligne de commande façon MS-DOS, en USB (Série) ou à distance (Telnet, port 23) ;
  • un site web (port 80) pour allumer et éteindre une LED ou un relais, et pour régler l'adresse IP ;
  • un serveur FTP (port 21) pour déposer et récupérer des fichiers sur la carte SD ;
  • un datalogger qui note chaque ON/OFF avec la date et l'heure dans un fichier CSV lisible dans Excel ;
  • une horloge Internet (NTP), des outils réseau (ping, tracert, netstat) et une configuration qui survit aux coupures de courant (EEPROM).

L'auteur est Jean-Marc Biechy (Institution Saint-Jean, école d'électronique, informatique et réseau, Colmar). Le programme fournit s'appelle PriseIP_UNOR4_jsWEB_SD_FTP_LogCmdLine_IDE2_v72 : version 72 du « socle ». Licence GNU LGPL v2.1.

Ce guide est écrit d'après le code source fourni (fichiers .ino, Shell_CmdLine_SD.h, ServeurWEB.h, utils.h, Driver_Ethernet_Reseau.h). Les messages affichés sont ceux du code, orthographe comprise.

Pourquoi on dit « OS »

Un Arduino n'a pas de système d'exploitation : un seul programme tourne, en boucle. IoToS ajoute les briques qu'on trouve dans un vrai système, en version minuscule :

Démarrage et boucle

Ce que fait setup()

Au branchement (ou après reset), la carte attend 2 secondes, puis déroule ceci. Chaque étape écrit une ligne dans le terminal Série.

  1. Ouvre le port Série à 115200 bauds et affiche la grande bannière rouge « IoToS ».
  2. Charge la configuration depuis l'EEPROM. Si elle n'est pas valide (mauvaise version du programme), recharge les valeurs d'usine.
  3. Configure les broches et remet la LED dans l'état sauvegardé.
  4. Initialise le bus SPI et la carte SD. Si la carte manque, l'erreur est affichée en blanc sur fond rouge et le FTP reste coupé.
  5. Initialise Ethernet : adresse MAC, IP fixe (avec test de cohérence IP / masque / passerelle) ou DHCP, puis détection du W5500 et du lien.
  6. Teste le DNS (résolution de www.google.com) puis récupère l'heure sur europe.pool.ntp.org. Sans Internet, l'heure reste inconnue.
  7. Lance les serveurs : Telnet (23), FTP (21, si la SD est là), WEB (port de la configuration).
  8. Affiche « System OK » et passe à la boucle.

Ce que fait loop()

La boucle tourne en permanence. Elle ne bloque jamais longtemps : chaque service fait un petit travail puis rend la main.

cmdLine.update()Lit le clavier Série et exécute les commandes tapées.
serverTelnetAccepte un client Telnet et lit ses commandes.
ServeurWEB()Si le WEB est ON : répond à un navigateur.
ftpSrv.handleFTP()Si la SD est là et le FTP ON : sert un client FTP.
BannièresAffiche l'écran d'accueil à la première connexion Série ou Telnet.
Conséquence du « coopératif » : une commande longue bloque le reste. Exemple : ping envoie 4 paquets en attendant 1 seconde entre chaque, donc pendant ~4 s le site web ne répond pas.

Les services

Ligne de commande (CLI)

Le même interpréteur sert le port Série (USB) et Telnet. Tu tapes commande argument, séparés par un espace. Il y a un historique de 10 commandes (flèches haut et bas, sans doublon consécutif) et la complétion par Tab : une seule possibilité, elle est complétée avec un espace ; plusieurs, la carte les liste puis charge la première, et chaque Tab suivant passe à la suivante ; aucune, elle bipe. Les noms de commandes ne tiennent pas compte des majuscules (PING, Ping et ping marchent), mais pas les arguments. Une ligne fait 127 caractères au maximum, et une commande inconnue répond Invalid command. Le CLI peut être verrouillé par mot de passe (login on) : les commandes sensibles répondent alors « Acces Refuse ».

Serveur WEB

Il sert deux pages stockées sur la carte SD : index.htm (commande de la LED, état en temps réel) et ConfIP.htm (réglage de l'IP). L'état de la LED se rafraîchit tout seul toutes les 10 secondes grâce à une requête AJAX. Un login Basic (Base64) est possible. Détails dans la section « Pages web et AJAX ».

Serveur FTP

Il donne accès à la carte SD pour mettre à jour le site ou récupérer les fichiers du datalogger. Identifiants d'usine : arduino / arduino. Ports : 21 pour le contrôle, 50009 pour les données (mode passif).

Datalogger

Quand il est ON, chaque changement d'état de la LED (par commande ou par le site web) ajoute une ligne au fichier choisi avec select : date;heure;ON ou OFF. Le fichier s'ouvre directement dans Excel.

type datalogger.csv Date ;Heure ; Etat Led 09/03/2026;22:17:31;ON 09/03/2026;22:17:34;OFF

Horloge NTP

Au démarrage, l'heure vient d'Internet. Elle sert à horodater le datalogger, à afficher « Date du dernier reboot » et l'heure dans print. Si le WAN est coupé : « WAN ERROR !! -- Serveur NTP (Real Time) : OFF ! ».

Tolérance aux erreurs réseau

Si l'IP fixe est incohérente (IP et passerelle dans des réseaux différents, masque se terminant par 255, IP identique à la passerelle, IP finissant par 0 ou 255), le démarrage affiche l'erreur et note que la carte « passe en DHCP ».

Toutes les commandes

La liste ci-dessous est générée à partir de la table commands[] du code. Le cadenas indique les commandes qui répondent « Acces Refuse » quand le CLI est verrouillé. Le bouton « essayer » exécute la commande dans l'onglet Terminal.

Pas à pas

Changer l'adresse IP

  1. Tape ip 192.168.0.2. La valeur est changée en RAM seulement.
  2. Tape print pour vérifier : la rubrique « Configuration Reseau en RAM » montre la nouvelle IP, celle de l'EEPROM l'ancienne.
  3. Tape save pour l'écrire dans l'EEPROM.
  4. Tape reset. La carte redémarre et prend la nouvelle IP. En Telnet, la connexion est coupée : reconnecte-toi sur la nouvelle adresse.

La même chose se fait depuis la page web « Configuration IP » : le bouton « Valider » enregistre en EEPROM et redémarre tout seul.

Sauvegarder et restaurer une configuration

  1. saveconf maconf écrit toute la configuration dans un fichier de la carte SD (297 octets).
  2. Plus tard, loadconf maconf la relit, la copie en RAM et dans l'EEPROM.
  3. Fais ensuite save puis reset pour que tout soit pris en compte, comme l'indique le message affiché.

Le fichier est lié à la version du programme : un fichier venant d'une autre version est refusé (« Mismatch »).

Journaliser les ON/OFF

  1. create mesures.csv crée le fichier avec son en-tête Excel Date ; Heure ; Etat LED.
  2. select mesures.csv le désigne comme fichier du datalogger.
  3. datalogger on active l'enregistrement.
  4. LED on, LED off ou les boutons du site web ajoutent une ligne. Chaque ajout affiche un cadre « Enregistrement Data » avec la taille du fichier.
  5. Lis le résultat avec type mesures.csv, ou récupère le fichier en FTP.

Récupérer des fichiers en FTP (FileZilla)

  1. Dans « Fichier → Gestionnaire de sites », crée un site : hôte = IP de la carte.
  2. Type d'authentification : « Compte ». Identifiant = nom de la connexion, mot de passe, et « Compte » = le login FTP (arduino d'usine).
  3. Onglet « Paramètres de transfert » : limite le nombre de connexions à 1 (la carte n'en gère pas plus).
  4. Sur Android, l'application AndFTP convient.

Verrouiller la ligne de commande

  1. password MonSecret choisit le mot de passe (d'usine : changerLeMotDePasse).
  2. login on verrouille. Les commandes sensibles répondent « Acces Refuse ».
  3. login MonSecret déverrouille (« IoTOS UNLOCKED !! »). exit reverrouille.
  4. À chaque mauvais mot de passe, le délai d'attente affiché double : 10 s, 20 s, 40 s… jusqu'à des jours.

Protéger le site web

  1. loginWEB on demande un identifiant et un mot de passe au navigateur.
  2. login-passWEB dXNlcjpwYXNz : la valeur est « utilisateur:motdepasse » encodé en Base64 (ici user:pass). Utilise un encodeur comme base64encode.org, par exemple admin:01_Admin donne YWRtaW46MDFfQWRtaW4=.
  3. save pour garder ces réglages après un redémarrage.

RAM, EEPROM, réseau actif : trois « versions » de la config

C'est le point qui surprend le plus. print en montre trois :

  • Configuration en cours : ce que le réseau utilise réellement depuis le dernier démarrage.
  • En RAM : ce que tes commandes ip, subnet… viennent de modifier. Perdu au redémarrage.
  • En EEPROM : ce que save a écrit. C'est ce que la carte relira après reset.
commandesip, name, LED… modifient la RAM
saveRAM → EEPROM
resetEEPROM → RAM → réseau actif
reloadEEPROM → RAM, sans redémarrer
defaultsusine → RAM et EEPROM

login on et login off écrivent aussi toute la configuration dans l'EEPROM. Le nom, le mot de passe et la plupart des réglages ne sont gardés qu'avec save.

AJAX signifie que la page n'a pas besoin de se recharger : un petit script interroge la carte et met à jour seulement l'état de la LED.

Login du site

Si loginWEB est ON, le serveur cherche dans les en-têtes la chaîne Base64 enregistrée (Authorization: Basic …). Absente : il répond 401 Unauthorized avec WWW-Authenticate: Basic realm="Secure", et le navigateur affiche sa boîte de connexion. Essaie dans l'onglet « Page web » après loginWEB on.

Le trafic est en HTTP clair, sans chiffrement. L'authentification Basic ne protège donc que contre un curieux sur le réseau local.

À savoir (limites et pièges)

Ces points viennent de la lecture du code, pas d'essais sur la carte. Ils expliquent des comportements qui peuvent surprendre.

  • Une IP mal écrite devient 0.0.0.0. ip 192.168.0 ne produit pas d'erreur : la commande confirme « IP 0.0.0.0 ». Même chose pour subnet et gateway. Vérifie avec print avant save.
  • pass n'est pas le mot de passe. C'est un synonyme de gateway (passerelle). Le mot de passe se règle avec password.
  • ping et tracert par nom. ping ne résout pas les noms DNS (il faut une IP : un nom devient 0.0.0.0 et ne répond pas). tracert les résout.
  • edit écrase le début du fichier. Il écrit le texte à partir de l'octet 0 du fichier choisi avec select, sans le vider ni ajouter à la fin. Sur un fichier CSV, il remplace les premiers caractères.
  • Le verrou du CLI n'est pas total. Certaines commandes ne le testent pas : help, ping, tracert, ram, version, save, reload, defaults, reset, login, exit. En particulier defaults remet les valeurs d'usine, mot de passe compris, même verrouillé.
  • Le bon mot de passe passe toujours. Le délai qui double ne fait qu'afficher un temps d'attente après une erreur ; il ne bloque pas un essai correct.
  • Les mots de passe sont affichés en clair par print (CLI, FTP) et par login on.
  • La MAC d'usine est …:B1. Le texte d'aide dit …:ED. Avec la MAC d'usine, le démarrage et print affichent un avertissement : deux cartes avec la même MAC sur un réseau se perturbent.
  • Le DNS affiché est écrit en dur (1.1.1.1) dans print.
  • Pas de formatage de carte : FormatSD est déclarée mais « non implémentée dans cette version ». Le watchdog, l'envoi de mails, l'OTA et le reset matériel (bouton D3) sont notés « off » dans les commentaires.
  • Un seul client FTP à la fois est géré : limite à 1 connexion dans FileZilla.

Ce que fait le simulateur

Sources : le code d'IoToS v72 de Jean-Marc Biechy (programme principal, Shell, ServeurWEB, utils, Driver Ethernet), la bibliothèque CmdLine v20 et des captures de la vraie carte. Le simulateur n'exécute pas le vrai firmware : c'est une reproduction en JavaScript de son comportement.

Reproduit d'après le code : la bannière et les lignes de démarrage (OK, FAILED et avertissements), l'écran d'aide, print, dir, tous les messages de confirmation et d'erreur des commandes, la différence RAM / EEPROM / réseau actif, le verrou et le délai de login, le datalogger avec ses fichiers CSV, les logs du serveur web dans le terminal, le login Basic du site, le rafraîchissement de la LED toutes les 10 s, la page de configuration IP et le redémarrage qui suit.

Approximé, mais réglable : les machines qui répondent au ping et leurs temps, les adresses obtenues en DHCP ou par DNS, la taille de la carte SD, la RAM et la date de compilation affichée par version se changent dans le panneau « Réglages de la carte simulée » de l'onglet Terminal. Approximé et fixe : le chemin de tracert et la date des fichiers de la carte. Les gros fichiers .htm sont tronqués par type.

Absent : le serveur FTP réel, l'écran LCD, le bouton matériel et tout ce qui touche au vrai réseau.

À propos du projet

Projet personnel de Leo, élève de Terminale CIEL : faire voir le micro-OS IoToS dans un navigateur, sans carte Arduino sous la main. La page contient un terminal, la page web de la carte et ce guide.

Démarche

  1. Comprendre ce qu'est IoToS : un micro-OS pour Arduino UNO R4 écrit par Jean-Marc Biechy.
  2. Réunir les sources : le code complet de la version 72, la bibliothèque CmdLine v20, les pages web et fichiers CSV de la carte SD, et des captures d'écran de la vraie carte en fonctionnement.
  3. Reproduire le comportement en JavaScript : démarrage, commandes, serveur web, EEPROM, login, datalogger.
  4. Vérifier : tests automatiques (démarrage, commandes, pages web, login, configuration IP, Telnet, pannes de SD et d'Internet) et relecture des messages face au code source et aux captures.
  5. Écrire le guide à partir du code, y compris ses limites et ses pièges.

Ce qui est reproduit et ce qui est approximé

Le détail est dans la section « Ce que fait le simulateur ». En résumé : tout ce qui est écrit dans le code est reproduit. Ce qui dépend de la vraie carte ou du réseau (adresses DHCP, temps de ping, taille de la carte SD…) est approximé, et réglable dans le panneau « Réglages de la carte simulée ». Le simulateur n'a pas été comparé en direct à une carte réelle : il se fonde sur le code et sur des captures.

Réalisé avec l'aide d'une IA

Le code du simulateur et la rédaction de ce guide ont été réalisés avec l'aide de Claude, une IA d'Anthropic, à partir des sources ci-dessus fournies par Leo. Les informations techniques viennent du code de Jean-Marc Biechy. Une IA peut se tromper : c'est pourquoi les approximations sont listées et pourquoi chaque comportement peut être vérifié dans le code d'IoToS.
